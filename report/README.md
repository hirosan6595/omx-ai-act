# OMX-AI 手首カメラ付き ACT 模倣学習 — 実験と解析のまとめ

期間: 2026-10-28 〜 10-29　／　対象: ROBOTIS OMX-F(フォロワー) + OMX-L(リーダー)、physical_ai_tools / lerobot、ACT ポリシー

## 1. 結論

| 項目 | 結果 |
|---|---|
| 最終モデル | `act-wrist-v1` の **030000**(通常版、`n_action_steps=100`) |
| 実機の成功率 | **14/15 = 93%**(俯瞰カメラのソフト補正あり、5 か所 × 3 回)。補正前(カメラを手で合わせた状態)は 11/15 = 73% |
| 位置別(補正あり) | 中央 3/3、左 3/3、右 3/3、手前 3/3、奥 2/3 |
| 成功率を上げた主因 | 推論時に leader の `joint_trajectory_command_broadcaster` を**無効化**したこと(有効では 0/61 回しか箱へ運べなかった) |
| その原因 | **グリッパへの指令の競合**。broadcaster がリーダーのグリッパ値(開)を送り続け、グリッパが閉じきれずに震え、キューブを保持できなかった |
| カメラ対策 | 俯瞰カメラの画像を、学習時の位置に合わせてソフトで補正(`cam_align_node.py`、§5.4)。手での合わせは難しく、時間とともにずれた |

### ひとことで言うと
> 推論時に leader の broadcaster を無効化したところ、箱まで運べなかった状態(0/61)から、約 7 割の成功に改善した。原因は、broadcaster がリーダーの「開いた」グリッパ値を同じトピックへ送り続け、モデルの「閉じる」指令と競合していたこと。

### 位置づけ(正直に)
- これは**モデルや学習の改善ではなく、実機側の問題を取り除いた**ものです。ACT の学習は lerobot の既定設定のまま、変えていません。
- 手首カメラの追加と再収集は、「学習が悪い」という誤診にもとづいて行いました。効果は**未確認**です(§5.3)。

### 分かっていないこと
- **腕の関節が、なぜ broadcaster の影響をほとんど受けないのか**(グリッパだけが強く影響を受ける)。軽いグリッパは指令の切り替えにすばやく反応し、重い腕は平均化される、という見立ては仮説。
- **左・奥が弱い理由**。学習データのキューブの多さ(40px 内: 左 20 > 右 16 > 中央 9 > 奥 8 > 手前 6)とは一致しない。各位置 n=3 なので、位置間の差は統計的に未確定。
- **手首カメラの効果**。オフライン検証では、手首画像を差し替えても予測がほぼ変わらない。v3(俯瞰のみ)の再試験は、条件の違いが残って結論が出なかった。

## 2. 経緯(時系列)

1. **再生で機械側の健全性を確認**: 録画した ep57 を再生 → 掴んで箱へ入れられた。
   - 以前の「FastBulkRead 通信断」は誤診。再生スクリプトが存在しないトピックへ送っていた。正しくは `/leader/joint_trajectory`(time_from_start=0)。
2. **俯瞰カメラのみの v3 で推論 → 掴めない**(上方でホバリング、「グリッパを閉じる動作がない」)。カメラ合わせ・TE 版でも改善せず。
3. **手首カメラ(camera2)を追加**して 80 本を再収集。「閉じたまま近づく」6 本を除く **74 本**で学習。
4. **ACT 学習**: batch 8、30000 ステップ。20000 で一度止め、再開。loss 0.348 → 0.125(20K) → **0.097**(30K)。
5. **実機推論 → やはり掴めない**。オフライン解析で切り分け(§4)。
6. 同じ位置での再現試験で、**broadcaster を無効にしたら成功**。
7. 合成指令(joint2 のみ)の実験で差が出ず、いったん「因果は未確定」と訂正 → ログ集計で **有効 0/61** と判明。
8. カメラが約 10°ずれていたことを発見し、合わせ直し → 位置別評価(73%)。
9. **グリッパの往復指令の実験で、競合の仕組みを特定**(§4.2)。
10. **v3 を broadcaster 無効で再試験** → 動作せず。ただし条件の違いが残る(§5.3)。
11. 手首版の状態へ戻し、成功を確認。

## 4. 原因の切り分け

### 4.1 検証の一覧
| 検証 | 方法 | 結果 |
|---|---|---|
| 学習データの再現 | `offl.py`: 学習データを入力し、予測と正解を比較 | 平均誤差 0.01〜0.06。モデルは学習データを再現できる |
| 手首カメラの寄与 | `offl2.py`: 別エピソードの画像・状態に差し替え | 手首画像の差し替えで、予測がほぼ変わらない |
| 入力の前処理 | `inference_manager.py` / `data_manager.py` を読む | 録画時と同じ。推論の観測はフォロワーの状態とカメラのみ(リーダーの指令は観測に入らない) |
| 指令の形式 | `data_converter.py` を読む | 推論の指令は `time_from_start=0`、`header.stamp=0`。broadcaster と同じ形式 |
| 同じ位置での再現 | ep42 の掴む直前まで再生 → キューブを置く → 逆再生で退避 → 推論 | broadcaster 有効で失敗、無効で成功 |
| 指令の発行元 | `ros2 topic info /leader/joint_trajectory -v` | 2 つ(broadcaster 100Hz、推論 30Hz) |
| 腕の追従 | `conflict.py`: joint2 に sin 指令(振幅 0.3 / 1.0 rad) | 有効/無効でほぼ同じ(誤差 0.09)。震えは有効が約 35% 大 |
| **グリッパの追従** | `conflict_g.py`: グリッパに往復指令(0.65 ↔ -0.15) | **有効時は開閉幅が 3 割弱、誤差 10 倍、1 秒に約 19 回震える**(§4.2) |
| 推論の周期 | ログの `Action data` の間隔 | どの条件でも約 30Hz |
| ログ集計 | 掴み→離すを 1 回とし、離す時 joint2>0.3 を「箱まで運べた」 | **有効 0/61、無効 約 23/73** |
| カメラのずれ | 基準画像と ORB+RANSAC で比較 | 回転 -13.6°、ずれ (-37, -46) px、倍率 0.918 → 合わせ直して合格 |

### 4.2 グリッパの競合(主因)
broadcaster は、リーダーの姿勢を、グリッパも含めて `/leader/joint_trajectory` へ 100Hz で送ります。リーダーのグリッパは開いた状態(約 0.65)です。フォロワーの `arm_controller` は、グリッパも制御します。

| | 無効 | 有効 |
|---|---|---|
| 実際の開閉幅(指令は 0.800) | 0.769 | **0.225** |
| 平均誤差 | 0.033 | **0.323** |
| 震え(2 階差分の RMS) | 0.0015 | **0.0136** |
| 動く向きが入れ替わる回数 | 0.9 回/秒 | **18.8 回/秒** |

観察との対応:
- 腕は掴む位置まで深く下りたのに、閉じ直しを何度も繰り返した → グリッパが閉じきれず、保持できなかった
- 箱まで運べたのが 0/61 → 保持できないので、運ぶ動作に進めない
- 動きが「ガタガタ」 → グリッパの震え
- v3 のころの「グリッパを閉じる動作がない」 → 閉じる指令が打ち消されていた可能性が高い

### 4.3 途中で訂正した主な誤り
- 「FastBulkRead 通信断」→ 再生スクリプトの送信先の誤り。
- 「発行元が 2 つで、腕が引き戻される」→ joint2 の実験で否定。**joint2 だけを動かし、グリッパを固定していたのが見落とし**。グリッパの実験で、競合を確認した。
- 「データ不足が失敗の原因」→ 左(データ最多)で失敗が多く、否定。
- ブラインド A/B は、カメラのずれ・キューブの位置・Policy Path の改行の混入で中断。ログ集計で代替した。
- v3 の基準画像(78 本の中央値)がぼやけていて、カメラ合わせの数値が ±2° 揺れた。鮮明な 1 枚に替えて、揺れは ±0.3° になった(§5.3)。

## 5. 実機評価

### 5.1 位置別(最終)
条件: 通常版 030000、broadcaster 無効、カメラ合わせ済み、各位置 3 回。

| 位置 | 座標(px) | 成功 | 失敗 |
|---|---|---|---|
| 1 中央 | (337, 273) | 3 | 0 |
| 2 左 | (241, 285) | 1 | 2 |
| 3 右 | (440, 277) | 3 | 0 |
| 4 奥 | (340, 246) | 1 | 2 |
| 5 手前 | (343, 329) | 3 | 0 |
| **計** | | **11** | **4** |

### 5.2 TE 版
`act-wrist-v1-te30` は、右・中央・左で成功したが、中央で下りきらずに揺れ続ける失敗も出た。試行数が少なく、通常版との優劣は未確定。

### 5.2b n_action_steps の比較
- `act-wrist-v1-n50` / `-n25`: 030000 の `config.json` の `n_action_steps` だけを 50 / 25 に変えたコピー(元の n100 は変更なし)。
- n50: 掴むまでは正常(joint2 0.06 まで下りる)。**運ぶ途中で予測し直すと、空中で止まり**(joint4 が約 1.0 → 0.45)、掴み直しを繰り返した。つなぎ目は約 1.7 秒ごとで、設定どおり動作していた。
- n25: n50 と同じ失敗(4.2 秒で深く掴み、持ち上げた後、空中で停止)。停止中のグリッパ状態は **-0.12** で、学習データの「持って運んでいる間」(約 **0.19** = キューブの幅で止まる)と違う。空振りか落下の可能性。
- 仮説: 予測し直すと、モデルは「空のまま閉じたグリッパ」という学習に無い状態を見て止まる(掴み損ねからの立て直しを学んでいない)。n100 は掴んだ後も 3.3 秒分をそのまま実行するので、影響を受けにくい。
- 結論: このモデルは、長いチャンク(n100)をそのまま実行するほうが安定する。滑らかさを上げるには、予測回数を増やすより、n100 のままチャンクのつなぎ目を補間する方向が有望(未実装)。
- RTC(Real-Time Chunking)は、フローマッチング系の方策(π0 など)向けで、ACT と lerobot 0.2.0 では使えない。

### 5.3 v3(俯瞰カメラのみ)の再試験
- 設定をカメラ 1 台に戻し、broadcaster 無効で、v3 の 030000 を試した → **動作せず**(98 秒でグリッパが 25 回開閉、掴む流れにならない)。
- v3 の学習データは、**カメラ位置が 2 通り**(ep 0〜38 と 39〜77。回転 1.9°、縦 20 px の差)。前者の位置に合わせた(回転 0.3°、ずれ 3 px、大きさ約 5% 差)。
- **結論は出ていない**。v3 の学習時と違う条件が残っている:
  1. アームに手首カメラとケーブルが付き、俯瞰から見たアームの姿が違う(手首カメラを外さないと解消できない)
  2. カメラの高さが約 5% 違う
  3. 机の上の配置が、v3 の録画時と違う可能性
- 試験後、手首版の状態(カメラ、2 台の設定)へ戻し、中央で成功を確認した。

### 5.4 俯瞰カメラのソフト補正(cam_align_node.py)
- カメラを手で合わせるのが難しく、30 分で大きさが約 6% 変わるなど、固定も安定しなかったため、**推論時に画像をソフトで補正**した。
- `open_manipulator` コンテナで動かす。`/camera1/image_raw/compressed` を購読し、基準画像(手首版の学習データ 74 本の開始画像の中央値)との相似変換を、起動時に 15 フレームで推定・固定する。`warpAffine` で補正し、`/camera1_aligned/image_raw/compressed` に 30Hz で配信。
- `omx_f_config.yaml` の camera1 を、補正後のトピックに変更(変更前は `omx_f_config.yaml.before_aligned_1029`)。
- 導入時: 5 か所のずれ(最大)が 約 27 px → **1.2〜2.2 px**。
- 推定し直すとき: アームを初期姿勢で静止させ、コンテナ内で `touch /tmp/cam_align_reestimate`。現在の変換は `/tmp/cam_align_state.json`。
- **自動起動**: systemd のユーザーサービス `cam-align.service` が `~/omx/cam_align/run.sh` を実行する。コンテナの起動を待ってノードを入れて起動し、落ちたら約 15 秒で起動し直す。推定した変換は `~/omx/cam_align/state.json` に保存され、次回の起動で読み込まれる(カメラを動かしていなければ推定し直さない)。
  - 推定し直す: アームを初期姿勢で静止させて `~/omx/cam_align/reestimate.sh`
  - 状態: `systemctl --user status cam-align` 、ログ: `journalctl --user -u cam-align`
  - 止める: `systemctl --user stop cam-align` 、自動起動をやめる: `systemctl --user disable cam-align`
  - ユーザーがログインしたときに起動する(Linger=no)。ログインせずに起動させたい場合は `loginctl enable-linger`。
- 注意: ノードが止まると、推論は camera1 を待って動かない。前後左右の傾きは補正できない。

| 2 左 | **3/3** | 1/3 |

## 6. 運用手順(実機推論)

> 「ホスト」= PC のターミナル。「サーバー」= `physical_ai_server` コンテナ。「ロボット」= `open_manipulator` コンテナ。

1. (ロボット)`omx_ai.launch.py` を起動。リーダーの自動起動が止まったら、`omx_l_leader_ai.launch.py port_name:=...` を手動で起動。
2. (ロボット)broadcaster を**無効化**:
   `ros2 control switch_controllers -c /leader/controller_manager --deactivate joint_trajectory_command_broadcaster`
3. (ホスト)`docker restart physical_ai_server` の後は、**手動で起動**(s6 のサービスが down のため):
   `ros2 launch physical_ai_server physical_ai_server_bringup.launch.py`
4. 俯瞰カメラの補正ノードは、自動で起動する(`cam-align.service`)。確認は `systemctl --user status cam-align`。カメラを動かしたら、アームを初期姿勢で静止させて `~/omx/cam_align/reestimate.sh`。手で合わせる場合の確認画面は `http://localhost:8090/align2.html`(5 か所のずれで判定)。
5. UI(`http://localhost`、F5)で、Policy Path を**一度空にしてから**入力。**末尾に改行を入れない**。
6. キューブを、机の印(`http://localhost:8090/targets.html` の位置)に置き、推論を開始。終わったら**停止**(1 回ごと)。
7. **録画するときは、broadcaster を有効に戻す**(`--activate`、または omx_ai.launch の再起動)。録画では、リーダーの動きをフォロワーへ伝えるために必要。

## 7. プログラム一覧(`scripts/`)

保存先: `~/omx/report/scripts/`。元は一時領域にあったため、**パスの一部(`/tmp/claude-1000/...`)が書き込まれています。使うときは書き換えてください**。

### ホスト(`scripts/host/`)
| ファイル | 内容 |
|---|---|
| `act_an.py` | 推論ログ(`Action data`)を読み、1 ステップの最大変化量と軌道を表示。0.1 未満=TE、0.4 超=通常版が目安。時刻の飛びで実行を区切り、最後の実行を解析 |
| `ev.py` | グリッパ指令が 0.1 を切った時刻を「掴む」、戻った時刻を「離す」として、その瞬間の関節姿勢を列挙 |
| `progress_loop.py` | 学習ログから進捗(step、loss、終了予定)を計算して JSON に出力 |
| `align_loop.py` | `/snapshot?topic=/camera1/image_raw` を基準画像と ORB+RANSAC で比較し、回転・ずれ・倍率を出力。直近 8 回の中央値で安定化。環境変数 `CENTER`、`TOL`、`MININL` で目標と許容幅を変更可 |
| `ab_watch.py` | broadcaster 有効/無効のブラインド A/B 用(試行の開始・終了を検知して条件を自動切替)。現在は使っていない |

### サーバーコンテナ(`scripts/container_server/`)
| ファイル | 内容 |
|---|---|
| `offl.py` | モデルをオフラインで動かし、学習データの予測と正解を比較 |
| `offl2.py` | 別エピソードの画像・状態に差し替えて、予測の変化を見る |
| `pick.py` | 掴む姿勢が中央付近のエピソードを選び、再生用 JSON を出力 |
| `gp.py`, `st.py`, `dist2.py` | 掴む姿勢の統計、状態と行動の差、joint1 の分布 |
| `mkref.py`, `mkref_v3.py` | 全エピソードの開始画像の**中央値**を、基準画像に出力(手首版 / v3) |
| `v3spread.py` | v3 データの各エピソードのカメラ位置の、ばらつきを測る |
| `v3ref2.py`, `v3ref3.py` | v3 データから、典型的なカメラ位置の鮮明な 1 枚を選ぶ。カメラ位置のグループ(A / B)を判別 |
| `v3B.py` | v3 のグループ B の基準画像を取り出す |
| `cube_pos.py` | 各エピソードのキューブ位置(オレンジ色の重心、机の範囲のみ)を検出 |
| `cmpimg*.py` | 学習データの画像の取り出し(比較用) |

### ロボットコンテナ(`scripts/container_robot/`)
| ファイル | 内容 |
|---|---|
| `replay_seg.py` | 録画した行動(JSON)を `/leader/joint_trajectory` へ 30Hz で再生。`<json> <start> <end>` |
| `gohome.py` | 現在の姿勢から初期姿勢へ、30Hz の連続指令で戻す |
| `conflict.py` | joint2 に sin 指令を送り、追従と震えを測る |
| `conflict_g.py` | 任意の関節(第 4 引数、5=グリッパ)に往復指令を送り、追従と震えを測る |
| `grab.py` | camera1 / camera2 の画像を 1 枚保存 |

### 画面(`web/`)
- `index.html`: カメラ合わせ(大きな表示、数値と案内つき)
- `targets.html`: キューブ位置の目安(5 か所)
- `progress.html`: 学習の進捗
- `refs/`: 基準画像。`ref_wrist.png`(手首版、使用中)、`ref_v3_A.png` / `ref_v3_B.png`(v3 の 2 つのカメラ位置)、`ref_v3.png`(v3 の中央値、ぼやけているので非推奨)
- 配信は `python3 -m http.server 8090`(画面と `align.json` を同じフォルダに置く)。

## 8. 落とし穴(再発防止)

- `docker restart physical_ai_server` 後は、サーバーを**手動で起動**。UI が Disconnected になる。
- Policy Path の貼り付けで、末尾に**改行**が入る(`does not exist or is not a directory`)。
- Policy Path を替えても反映されないことがある → サーバー再起動 + 欄を空にして入れ直す。
- 推論後、アームが空中で止まる。次の推論は**初期姿勢**から始める(`gohome.py`)。
- broadcaster が有効だと、単発の長い指令(`replay_seg.py` の最初の移動)は上書きされて動かない。
- フォロワーの電源切れ / USB の再接続(ttyACM の番号が変わる)で、通信が落ちる。電源を確認後、`omx_ai.launch` を `SIGINT` で止めて再起動。
- `pkill -f` は自分自身の bash も殺す。先頭固定のパターン(`^python3 ...`)を使う。
- 手首カメラは `v4l2-ctl --set-ctrl=exposure_dynamic_framerate=0` で 30Hz を維持(再接続でリセットされる)。
- キューブをロボットの根元に近づけすぎると失敗(学習データに無い範囲)。
- カメラ合わせの基準に、カメラ位置がばらついたデータの中央値を使うと、画像がぼやけて測定が揺れる。鮮明な 1 枚を使う。

## 9. 次の課題

1. **補正ありで、回数を増やして成功率を確認**(各 5〜10 回、特に奥)。失敗の種類(浅い掴み / 位置ずれ)をログで分ける。
2. 推論の実行中に、グリッパの**指令と実際の位置**を記録し、保持の失敗を直接確かめる。
3. 腕の関節がグリッパほど影響を受けない理由(Dynamixel の設定の比較など)。
4. 手首カメラの効果の検証(手首カメラを外して v3 を試す、など)。
5. 成功率を上げる本質的な改善: 画像のデータ拡張、左・奥のデータ追加、手首カメラの寄与を高める工夫、評価の整備。
6. TE 版・途中のチェックポイントとの比較。
